# 前言

经过前面章节的学习，我们对于基础的rust嵌入式开发过程已经有了一定的认识与实践。即便是尚未涉及到的外设，我相信各位读者也能举一反三地通过参考官方文档进行开发。

因此，接下来我们要学习的是，rust的并发模型——**异步编程**。

对于多任务场景，在传统的嵌入式开发中，常用的解决方案是RTOS或Linux，通过系统内核实现多任务并发调度。对于rust下嵌入式并发场景，虽然也可以使用RTOS方案，但其自身的语言特性`async/await`，为嵌入式并发提供了一个**更轻量、更高效、更现代**的，也是rust社区更为推崇的方案——异步并发。

# 异步是什么

简单来说，**异步就是“不阻塞等待”**。在同步编程中，调用一个耗时函数，例如延时1000ms，CPU 就会停在那里空转，直到1000ms结束才执行下一行代码。而在异步编程中，同样调用一个耗时操作，CPU 不会傻等，而是会**立刻转去执行其他任务**，直等延时结束，它再回来继续执行后面的代码。

在rust的原生语法特性中：

- `async fn` 定义一个可被挂起和恢复的任务函数。

- `.await` 是一个主动让出 CPU的挂起点，如果当前操作尚未就绪，任务就主动让出 CPU，去执行其他任务。

# 为什么是异步

为什么rust选择异步而不是传统的RTOS呢？

- **语言的原生支持**：Rust语言本身就内置了`async/await`异步语法。异步模型和Rust的所有权系统、生命周期等特性天然契合，能实现编译期的内存和线程安全检查，这几乎是“官方指定”的并发方案。

- **极致的资源效率**：传统 RTOS 的任务都需要分配固定大小的栈空间，任务切换需要内核介入，保存和恢复上下文，开销较大。Rust 的异步任务是**无栈**的，在编译时被编译为一个状态机，只保存当前执行到`await`点的局部变量，因此内存开销可以极小，且多个异步任务可以**共享同一个系统栈**，任务切换也没有内核参与。异步的轻量特性，使其能够支持远超RTOS任务数量的并发单元。

```rust
// 你写的代码：
async fn example(x: u32) -> u32 {
    let a = read_sensor().await;  // 状态 0 → 1
    let b = a + x;                // 状态 1
    let c = send_data(b).await;   // 状态 1 → 2
    c + 1                         // 状态 2
    ......                        
}

// 编译器生成类似这样的结构：
enum ExampleStateMachine {
    State0 { x: u32 },
    State1 { x: u32, a: u32 },
    State2 { x: u32, a: u32, b: u32 },
    ......
    Done,
}
```

- **现代的开发体验**：相比手动编写复杂的状态机或中断处理，`async/await`能让开发者用**近乎同步的代码风格编写并发逻辑**。

# 如何实现

**rust的异步机制由任务(Future)、唤醒器(Waker)和执行器(Executor)组成。**任务自己决定何时暂停与恢复，唤醒器负责在任务就绪时通知执行器，执行器负责在任务暂停时调度其他任务运行。

1. **`Future` 特性与`async`/`.await`**

一切异步操作都始于`Future` 特性，表示**未来某个时刻会完成计算并返回的值**。`poll`是`Future`特性的核心方法，执行器通过调用它来推进任务，用于获取任务的执行情况。`poll`会返回：

- `Poll::Ready(value)`：任务已完成，并返回结果 `value`。

- `Poll::Pending`：任务暂时无法完成，需要等待某个事件。

直接手动实现 `Future` 较为繁琐。因此，Rust 提供了更为便利的`async`/`.await`语法糖，让异步代码写起来像同步代码一样直观。

- `async`：当你在一个函数前写上 `async fn`，编译器会将其转换成一个实现了 `Future` 特质的**状态机**。每个 `.await` 点都是这个状态机的一个状态。

- `.await`：在 `.await` 处，如果 `Future` 返回 `Poll::Pending`，当前任务会被挂起，交出控制权，当 `Future` 就绪后，会被`Waker` 唤醒并再次轮询。
2. **`Waker` 与事件驱动**

`Waker` 负责在任务可以继续执行时“唤醒”它。当一个 `Future` 返回 `Pending` 时，它会将 `Waker` 注册给某个事件源（如定时器、串口中断）。当该事件发生时，事件源会调用 `Waker` 的 `wake()` 方法。`wake()` 被调用后，执行器就知道这个 `Future` 可以再次被 `poll` 了。这避免了执行器无意义地轮询所有任务，实现了**事件驱动**。

3. **`Executor`与任务调度**

`Executor` 是一个执行器，负责管理并驱动 `Future`执行。一个典型的执行器会循环执行以下操作：

1. 找出一个可执行的 `Future`（例如刚被 `Waker` 唤醒的）。

2. 调用它的 `poll` 方法。

3. 如果返回 `Pending`，就把它放回队列，等待下次唤醒。

4. 如果返回 `Ready`，就将其标记为完成。

# 主流异步框架

从异步编程在rust中的实现可以得知，执行器是实现多任务并发调度的关键。但是rust中并没有实现执行器，而是选择交由第三方提供。

而在嵌入式场景中，**`Embassy`**是最主流的一个现代化嵌入式异步框架。它提供了**执行器**来调度任务，以及**硬件抽象层**来操作外设。

需要注意的是，`Embassy`**并不适合需要严格硬实时保证的场景**，它是软实时协作式调度，需要主动让出CPU。这意味着并发调度的响应速度有限，且实时性完全依赖开发者的代码设计，糟糕的代码即便在异步框架下也会被严重阻塞。

因此除了`Embassy`之外，rust还有另一种**硬实时的异步框架`RTIC`**。

- 机制：在代码中定义中断处理程序（ISR）的优先级。当高优先级的外设中断触发时，CPU 硬件会立即打断当前正在执行的任务（**即使它在 .await 点中间**），去执行中断服务函数。

- 实时性：响应延迟取决于 CPU 中断响应的硬件特性（通常是纳秒到微秒级），而**不依赖于任务是否主动让出**。这保证了高实时性任务绝对不会被其他业务逻辑阻塞。

在实际项目当中，这两种框架是可以混合使用的，这也是社区及工业中推荐且常见的做法。

## 与RTOS对比

| 对比维度      | 传统RTOS (如 FreeRTOS)               | Rust 异步 (如 Embassy)                 |
| --------- | --------------------------------- | ----------------------------------- |
| **调度方式**  | **抢占式**：高优先级任务可随时打断低优先级任务。        | **协作式**：任务必须主动让出CPU。                |
| **实时性**   | **硬实时**，可预测，优先级明确。                | **软实时**，难以预测，依赖于代码设计。               |
| **上下文切换** | **由内核调度**：开销相对较大，需要保存和恢复完整的任务上下文。 | **在`.await`点进行**：开销极小，仅需切换状态机。      |
| **内存占用**  | **较高**：每个任务的堆栈都会占用RAM。            | **极低**：一个任务可能仅需**几十个字节**，所有任务共享一个栈。 |
